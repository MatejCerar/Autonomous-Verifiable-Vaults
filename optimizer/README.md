# optimizer/ - AVV quant core

The risk-adjusted yield optimizer for the Automated Verifiable Vault (AVV). Given a
snapshot of the three Mystic / Morpho supply markets (FXRP, USDT0, WFLR) it decides
how to split a stablecoin-denominated vault of capital C across those venues plus a
defensive reserve, to MAXIMIZE risk-adjusted yield under hard caps. The output is
later serialized into a signed Plan (see `../schema/preimage.md`), signed by the
TEE, and enforced on-chain against the same caps by `CurationController`.

Files:

- `EQUATION.md`  - full derivation: yield-curve model, objective, constraints, KKT,
  water-filling result, worked example, live-data result, sensitivity discussion.
- `optimize.py`  - reference implementation (numpy optional; pure-Python fallback).
  Loads `../research/market-data.json` if present, else a labeled SAMPLE; prints an
  allocation table and writes `result.json`.
- `optimize.ts`  - TypeScript port with identical math. Pure, deterministic, no
  network. Exports `optimize(marketData, params) => OptimizeResult`.
- `result.json`  - the optimizer output (schema below). Regenerated by running the
  Python entrypoint.

## What it computes (one paragraph)

Each market has a diminishing supply-yield curve: supplying a deposit d_i lowers
utilization u_i = B_i / (S_i + d_i), and the AdaptiveCurveIrm-style borrow rate maps
that utilization to a supply APY r_i(d_i) that FALLS as you add deposit. The
optimizer maximizes J(w) = sum_i w_i r_i(w_i C) minus a variance penalty
(lambda/2) w^T Sigma w, subject to a budget (weights + reserve = 1), a per-venue cap
(default 0.30), a total-out cap (default 0.80), a reserve floor (default 0.20), and a
per-venue liquidity/depth cap. At the optimum the funded, unclamped venues equalize
their risk-adjusted marginal yield (water-filling); caps and liquidity act as clamps.
See `EQUATION.md` for the KKT derivation.

## Run it

### Python (reference; writes result.json)

```
cd optimizer
python3 optimize.py
```

numpy is optional. If it is installed it is used for the covariance product; if not,
a pure-Python fallback runs the identical math. To get numpy in the sandbox VM:
`nix profile install nixpkgs#python3Packages.numpy` (the script also runs fine
without it). The script loads `../research/market-data.json` if present, otherwise
the built-in labeled SAMPLE, prints the allocation table, and writes `result.json`
with `"dataSource"` set accordingly.

### TypeScript (same math; used by the tee-model service)

`optimize.ts` has no runtime dependencies. Import `optimize` and call it:

```ts
import {optimize, SAMPLE_MARKET_DATA} from "./optimize.ts";
import {readFileSync, existsSync} from "node:fs";

const md = existsSync("../research/market-data.json")
  ? JSON.parse(readFileSync("../research/market-data.json", "utf8"))
  : SAMPLE_MARKET_DATA;

const res = optimize(md);            // defaults: cap 0.30, maxTotalOut 0.80,
console.log(res.weights, res.reserve); // reserveFloor 0.20, lambda 0.10, C 1e6
```

Run a file with `tsx` (bundled in `../tee-model/node_modules`):

```
../tee-model/node_modules/.bin/tsx your-runner.ts
```

Override any parameter via the second argument, e.g.
`optimize(md, {lambda: 0.5, capital: 2_000_000, cap: 0.25})`.

## Input schema (consumed)

The optimizer accepts the research worker's `market-data.json` (assets as an array,
correlation under `pairwiseCorrelation.{order,matrix}`, `irm.{targetUtilization,
curveSteepness}`) AND the built-in SAMPLE (assets keyed by symbol, plain
`correlation` matrix). Per asset it reads, in order of preference:

- market state: `totalBorrowAssets` + `totalSupplyAssets`, else `utilization` +
  `tvlUsd`, else `utilization` + `availableLiquidity(Usd)`. Missing -> idle market.
- `supplyApy` (or `supplyApyOnchainComputed`): the reported net supply APY; used to
  CALIBRATE the venue's `rateAtTarget` so the model reproduces it at the current
  utilization. If absent, a default `rateAtTarget` is used (labeled as an assumption).
- `availableLiquidityUsd` (or `availableLiquidity`): tightens the per-venue cap to
  `min(cap, liquidity / C)` (market depth).
- `annualizedVol`: floored at `depegVol` (0.02) for stablecoin-like legs.
- `priceUsd`, `decimals`, `venueId`: for the USD-to-token conversion and on-chain
  mapping.

Every missing field degrades gracefully and is recorded in `result.assumptions`.

## Output schema (`result.json`)

```
{
  asOf, chainId (14), dataSource,        // provenance; "SAMPLE" if no live data
  capital,                               // C, USD notional
  params: {cap, maxTotalOut, reserveFloor, lambda, reserveApy, uTarget, curveSteepness},
  weights: {FXRP, USDT0, WFLR},          // fractions of C
  reserve,                               // fraction of C (>= reserveFloor)
  expectedApy, expectedRiskAdjApy,       // portfolio APY and APY minus variance pen
  perVenue: [{symbol, venueId, weight, amountUsd, tokenAmount, decimals,
              supplyApyPostDeposit, marginalYield, bindingConstraint}],
  waterLine,                             // common risk-adj marginal yield (nu)
  assumptions: [...],                    // every degraded/assumed input, labeled
  rationale                              // one-line human explanation for the UI
}
```

`bindingConstraint` is one of: `"venue cap"`, `"liquidity"`,
`"interior (on water line)"`, `"excluded (below water line)"`.

## Mapping weights to on-chain amounts

The vault and Plan work in wei and bips (see `../schema/preimage.md`). To turn an
optimizer result into a Plan:

1. Per-venue USD notional: `amountUsd_i = weight_i * C` (already in `perVenue[i].amountUsd`).
2. Per-venue TOKEN amount (human units): `tokenAmount_i = amountUsd_i / priceUsd_i`
   (already in `perVenue[i].tokenAmount`).
3. Per-venue WEI for `Allocation.amount`:
   `amountWei_i = round(tokenAmount_i * 10^decimals_i)`.
   Example from the live `result.json`:
   - USDT0: 300000 USD / 1.0 = 300000 tokens, decimals 6 -> 300000 * 1e6 =
     `300000000000` wei.
   - WFLR: 31759 USD / 0.0059951 = 5297492.9526 tokens, decimals 18 ->
     approximately `5297492952577938802343936` wei (integer; compute at full
     precision on-chain / in the signer, do not round the human display value).
   - FXRP: 84750 USD / 1.013054 = 83657.9294 tokens, decimals 6 ->
     `83657929390` wei.
4. `Allocation.venueId = perVenue[i].venueId` (index-aligned with the on-chain
   adapter order in `../tee-model/src/inputs.ts`).
5. `reserveAmount = round(reserve * C_inVaultUnits)` routed to the ReserveAdapter.
6. `totalOut = sum(allocations) + reserveAmount`. With the defaults, sum(weights) +
   reserve = 1, so `totalOut` equals the full vault base being planned this cycle.

Cap enforcement is dual: the optimizer already keeps every `weight_i <= cap` and
`sum(weights) <= maxTotalOut` and `reserve >= reserveFloor`, and the contract
re-checks the same as bips of TVL (`venueCapBips`, `maxTotalOutBips`,
`minReserveBips`). Because the optimizer respects the caps, a good plan always
passes the on-chain checks; the on-chain checks exist to reject a tampered or
buggy plan (they revert before any funds move).

Note on units: the demo vault holds a single stablecoin-denominated base asset, so
"USD notional" and "vault units" coincide up to that token's decimals. If a venue's
supplied token differs from the vault base (as in the live Mystic Core vaults, where
each vault is single-asset), the adapter handles the vault-base-to-venue-token
routing; the optimizer's `amountUsd` is the USD size and `tokenAmount` is the venue
token size at the given `priceUsd`.

## Verification

- `optimize.py` and `optimize.ts` produce bitwise-identical weights on both the
  SAMPLE and the live `research/market-data.json` (max |weight difference| = 0,
  reserve/APY/riskAdjAPY differences = 0). Cross-checked by running both and
  diffing the JSON.
- The solver output is validated against a fine brute-force grid over the feasible
  box (matches to 1e-9 on both inputs), confirming global optimality for this
  concave 3-asset problem.
- Constraints are asserted in the Python entrypoint's printout: `sum(weights) +
  reserve = 1`, every `weight <= cap`, `sum(weights) <= maxTotalOut`, and
  `reserve >= reserveFloor`.
